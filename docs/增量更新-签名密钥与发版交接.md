## 1. 一句话现状

自 v6.8.4 起，应用升级支持**增量更新**（只下载变化文件，MB 级），失败自动回退全量。
该功能依赖一对 ed25519 密钥：**私钥签名 patch、公钥验签**。私钥绝不能丢、绝不能入库；
公钥随 EXE 部署到用户数据目录。

## 2. 签名密钥（关键，务必按此操作）

### 2.1 当前有效私钥 —— v6.8.4 起生效

- **算法**：ed25519，私钥为 64 字符 hex。
- **存放位置（两处，均不入库）**：
  - `C:\Users\Administrator\Downloads\cv-update-signing-key.hex`
  - `D:\ai program\local-movie-library\.keys\update-signing-key.hex`（`.keys/` 已在 `.gitignore` 忽略）
- **本文不记录私钥值**。任何回复/日志/文档都不要打印它。
- **签名时怎么读**：发布前在 shell 里
  `export CV_UPDATE_SIGNING_KEY=$(cat "C:/Users/Administrator/Downloads/cv-update-signing-key.hex")`，
  再跑 `packaging/_cv_patch.py gen-patch`（脚本从环境变量读；无该 env 则生成**未签名** patch，客户端会拒收）。
- **铁律：后续每个版本的 patch 必须用这一把私钥签。** 换私钥 = 所有老用户验不过新 patch。

### 2.2 历史教训（为什么存两处）

最初的私钥只存在 Downloads，会话重置时 Downloads 被清理导致私钥丢失，只能换钥（v6.8.3→v6.8.4 换的）。
所以现在私钥双份存放（Downloads + 仓库外 `.keys/`），且 `.keys/` 已 gitignore。
**接手第一件事：确认上面两处至少有一处存在且内容一致**；若都丢失，必须走"换钥流程"（见 §5）。

### 2.3 验签公钥（公开信息，可入库）

- 文件：`packaging/update-public-key.pem`（PEM，公开，**不是凭据**）。
- 部署链：`prepare-export.js` 把它复制进 `packaging/payload/update-public-key.pem`
  → EXE 打包时 payload 进 `resources/payload/`
  → `packaging/main.js` 启动时同步到 `<DATA_ROOT>/updates/update-public-key.pem`
    （**每次启动比较内容，不同才覆盖**——这样换钥后老用户启动新版会自动拿到新公钥）
  → `utils/updater.js::readUpdatePublicKey()` 读它（`CV_UPDATE_PUBLIC_KEY` 环境变量优先，再读该文件）。
- 用户双击 EXE 无需任何配置即可启用增量；缺公钥时优雅回退全量下载。
- 手动轮换公钥：设 `CV_UPDATE_PUBLIC_KEY` 环境变量（env 优先于文件）。

## 3. patch / manifest 生成与验签约定

- 生成：
  ```
  python packaging/_cv_patch.py gen-manifest --root . --version <VER> --out packaging/out/cv-manifest-<VER>.json
  python packaging/_cv_patch.py gen-patch --root . --baseline <上版manifest> --target <本版manifest> \
      --out packaging/out/cv-patch-<from>-<to>.zip
  ```
  产物放 `packaging/out/`，被 `packaging/_r23-release.py` 的 `_extra_assets()` 自动发现并随 Release 上传。
  发布前把 out/ 里**旧版本**产物移走（如 `out/_old/`），否则会被一并上传。
- **baseline 必须用真实上版发布镜像 `git/` 导出**，不要用本地 commit 树——本地树缺大量工作区未提交文件，
  会误判成上百个 added、patch 虚高到 8MB；用 `git/` 导出后 patch 只有几十 KB。
- 客户端硬编码文件名：`cv-manifest-<ver>.json`、`cv-patch-<from>-<to>.zip`（ver 去掉 v 前缀）。
- **跨语言字节契约（改动前必看）**：patch.json 签名负载 =
  `{version, added, modified, removed, sha256}` 五字段。
  Python `_cv_patch_lib.py::_canonical()`：`json.dumps(sort_keys=True, separators=(',',':'), ensure_ascii=False).encode('utf-8')`；
  Node `incremental-updater.js::canonical()`：递归按码点排序、无空格、UTF-8。两端字节必须完全一致，
  测试里有真实 Python 签→Node 验 roundtrip（含中文/嵌套键），改任一端都要重跑。
- 安全：SSRF 复用 `assertSafeUrl()`；zip-slip 三层防护；不执行下载内容；主进程执行原子切换 + 失败回滚。

## 4. 发版流程（PC，含增量）

```
# 1) 升版本号（6 处：两份 package.json/lock、_r23-release.py 的 VER/TAG、_r23-publish.py 的 TAG/正文）
# 2) 生成 manifest + 签名 patch（见 §3）
# 3) 构建
cd packaging && node prepare-export.js && npm run dist
# 4) 同步镜像（不要 --prune，否则删 LICENSE/README）
cd .. && python packaging/_sync-public.py --apply
# 5) 推仓库 + 打 tag + 发 Release
python packaging/_r23-publish.py check && python packaging/_r23-publish.py push
python packaging/_r23-release.py
```
- 远端 `main` 是逐版快照仓，不要对远端 main 开普通 PR。
- git https 直连在本环境超时：git 操作用 `git -c http.proxy=http://127.0.0.1:7892 push ...`；API 脚本走系统代理正常。
- 凭据从 git credential manager 取，不要用 `gh`（gh 要 `read:org` scope，现有 token 没有）。

### ★发版验收铁律：必须真 GUI 启动（2026-11-22 血泪教训）

6.8.3 曾经发布后**完全无法启动**：`main.js require('./incremental-switch')` 找不到模块——
新建的主进程模块没加进 `packaging/package.json` 的 `build.files` 白名单，打包后 `resources/app/` 没有它，
主进程启动即崩溃弹窗。当时无显示器、GUI 冒烟拿不到日志就被当成环境问题跳过，导致坏版发出去。

**以后每次发版，必须实际启动 EXE 并确认：**
1. 主进程不弹 "A JavaScript error occurred in the main process" 错误框；
2. `<DATA_ROOT>/runtime/app-version.json` 写入正确版本；
3. `%TEMP%\cinemavault-boot.log` 出现"系统托盘已创建""全局快捷键已注册""已同步增量验签公钥"；
4. `<DATA_ROOT>/updates/update-public-key.pem` 落地且与 `packaging/update-public-key.pem` 一致；
5. `server.log` 有"本地影库服务启动成功"。

有显示器时可用隔离数据目录启动脚本（仓库外 `C:\Users\Administrator\Downloads\cv_launch_684.py`，
改其中的 DATA 路径即可复用）。**新增任何主进程 `require` 的 .js 文件，必须同步加进 `build.files`。**

## 5. 换钥流程（仅当私钥确实丢失时）

1. 生成新 ed25519 密钥对：私钥 64 字符 hex 写 §2.1 两处，公钥 PEM 覆盖 `packaging/update-public-key.pem`。
2. 因为 `main.js` 每次启动会同步公钥（内容不同才覆盖），老用户升级到新版后公钥自动刷新为新公钥，
   **前提是新版本 EXE 必须真正发布让用户升级**；用旧版 + 新 patch 的用户会验签失败并回退全量（安全）。
3. 用新私钥重签本版 patch，并用新公钥做一次 Python 签→Node 验 roundtrip。
4. 走 §4 流程发新版本；旧坏版在 Release 正文加醒目标注。
