# 增量热更新（B 方案）设计草案

> 生成：2026-11-21
> 状态：**设计草案，未实现**。供后续迭代（Claude）落地。
> 背景：A 方案（多源镜像 + SSRF 防护）解决「能下载」；本文解决「不必每次全量下载 180MB」。

---

## 1. 目标与边界

**目标**：版本升级时只下载「变化的文件」，把更新包从 ~180MB 降到几十 KB～几 MB，秒级完成；失败可回滚，不破坏现有可运行版本。

**边界（先说清什么不适合差量）**：
- ✅ 适合差量：`public/**`（HTML/CSS/JS）、`routes/**`、`utils/**`、`server.js`、`package.json` 等纯文本源码。
- ⚠️ 谨慎差量：带原生模块（`.node`）或 `node_modules` 的依赖——ABI 与平台相关，建议按「整目录哈希变化 → 整包替换」而不是逐文件。
- ❌ 不适合差量：Electron 主进程二进制、`.exe` 本身、SQLite 数据库、用户数据。这些走**全量回退通道**。

**双通道原则**：增量失败（校验不过 / 校验和缺失 / 网络断）→ 自动回退到 A 方案的多源全量下载。增量永远是「加速」，不是「唯一路径」。

---

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| **release manifest** | 每个版本发布时生成一个 `manifest.json`，列出所有可差量文件的相对路径 + sha256 + 字节数。 |
| **baseline 版本** | 用户当前版本。把它安装时的 manifest 作为对比基准。 |
| **patch 包** | 目标版本相对 baseline 的「新增/修改/删除」文件集合，打成一个 zip，附每个文件的 sha256。 |
| **原子切换** | 下载解压到 staging 目录 → 校验全部哈希 → 停后端 → 备份当前版本目录 → 替换 → 重启。任一步失败从备份回滚。 |

---

## 3. manifest 格式（建议）

发布产物在 GitHub Release 额外挂一个 `cv-manifest-<version>.json`（几 KB），与全量 EXE 一起上传：

```json
{
  "version": "6.8.2",
  "generatedAt": "2026-11-22T...",
  "files": {
    "public/js/app.js":      { "sha256": "ab...", "size": 92031 },
    "public/css/style.css":  { "sha256": "cd...", "size": 40122 },
    "routes/novel.js":       { "sha256": "ef...", "size": 22010 }
  },
  "binaryDirs": ["node_modules/better-sqlite3"],
  "fullFallback": {
    "setup": "CinemaVault-Setup-6.8.2.exe",
    "portable": "CinemaVault-Portable-6.8.2.exe"
  }
}
```

---

## 4. 差量计算与 patch 生成

发布流水线（`packaging/_r23-release.py` 扩展，或新脚本 `_patch.py`）：

1. 从 GitHub 取上一个正式版本的 manifest（`baseline`）。
2. 扫描当前发布树的可差量文件，算 sha256。
3. `added` / `modified`（哈希不同）/ `removed`（baseline 有、当前没有）。
4. 打包 `cv-patch-<from>-<to>.zip`：
   - `changed/` 存新增/修改文件（保持相对路径）；
   - `removed.json` 列出要删的相对路径；
   - `patch.json` 存目标版本、每个文件 sha256、总字节数。
5. 把 patch 与 manifest 一起挂到 Release（体积通常 < 5MB）。

**多 baseline**：可对最近 N 个版本（如 3 个）各生成一个 patch；太旧的版本强制走全量。manifest 里声明 `minPatchFrom`。

## 5. 客户端升级流程

```
POST /api/update/check            → 拿最新 manifest（小，可高频查）
本地读 baseline manifest            → diff
若无 patch 或 baseline 太旧         → 直接走 A 方案全量
POST /api/update/incremental-start → 后端下载 patch（复用 A 的多源 + SSRF）
解压到 <DATA_ROOT>/updates/staging-<version>/
逐文件校验 sha256
校验通过:
  停后端 → 备份当前可差量文件到 rollback-<version> → 覆盖 → 重启 → 上报成功
校验失败:
  删除 staging → 自动回退全量下载
重启后发现异常:
  从 rollback-<version> 恢复 → 上报失败
```

## 6. 安全（必须实现，不能省）

1. **文件校验**：patch 内每个文件按 `patch.json` 的 sha256 逐个校验；manifest 本身用发布私钥签名（ed25519），客户端用内置公钥验签，防篡改。
2. **路径穿越**：解压时校验每个条目解析后必须落在 staging 目录内，拒绝 `../` 与绝对路径（zip-slip）。
3. **下载源**：完全复用 A 方案的 `assertSafeUrl`（仅 http/https、拒绝 localhost/环回/私网/保留地址、302 后复检）。
4. **不执行下载内容**：patch 只写文件，绝不 `require`/`spawn` 其中的脚本；重启走正常启动流程。

---

## 7. 回滚与幂等

- 每个版本目录保留最近 1 份 rollback 备份，成功运行 24h 后清理（可配置）。
- 升级操作加文件锁，禁止并发；中断后重跑能从 staging 或 rollback 恢复。
- 记录 `update-state.json`：`{baseline, target, phase, ts}`，phase  ∈ `downloading|verifying|swapping|done|rolled_back`，供前端展示与故障排查。

---

## 8. 落地里程碑（建议顺序）

| 阶段 | 交付 | 验收 |
|---|---|---|
| M1 | manifest 生成 + Release 上传 | 每个版本有可下载的 manifest，哈希与实际一致 |
| M2 | 客户端 diff + patch 下载校验（不切换） | 能算出 patch、下载并校验通过，不覆盖任何运行文件 |
| M3 | 原子切换 + 回滚 | 模拟校验失败/切换中断，均能恢复原版本 |
| M4 | 前端进度与「回退全量」按钮 | 增量失败时用户无感切全量，或手动选全量 |
| M5 | 多 baseline + 旧版本全量策略 | 3 个版本内增量，更旧自动全量 |

---

## 9. 与 A 方案的关系

- A 方案（`utils/updater.js` 的 `assertSafeUrl` + `candidateDownloadUrls` 多源回退）是**基础设施**：B 方案的所有下载都复用它，无需重复实现安全与加速。
- A 已先落地并验证；B 作为下一迭代，按上面 M1→M5 推进。
- 两者都不改变发布形态（仍是 GitHub Release + 手工上传 API），不引入额外服务。

---

## 10. 风险与开放问题

- **二进制/原生模块**：better-sqlite3 等 ABI 绑定，差量需小心；M1 先只覆盖纯文本，二进制目录走整目录哈希判断。
- **用户改过文件**：若用户手动改过 `public/**`，差量会覆盖。需在升级前提示，或只差量「未本地修改」的文件（用 baseline manifest 校验当前文件哈希，改过的跳过并告警）。
- **签名私钥管理**：ed25519 私钥不能入库；发布时从环境变量/密钥服务读取（遵循凭据约束）。
- **断点续传**：patch 小，暂不做；全量通道的断点续传可作为独立改进。
