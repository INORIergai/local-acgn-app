> 调研对象：`CinemaVault-v4.5.6-Android.apk`（versionCode 3 / minSdk 24 / targetSdk 34 / Java 单 Activity WebView 壳）+ 它依赖的手机端网页层 + 服务端分发链路

> 时间：2026-10-22 ｜ 约束：全部只读，未改动任何源码、未启动服务

## 0. 一句话结论

**这个 App 的功能已经跑在「够用」线上（影/漫/书/听书/弹幕四合一，形态罕见），问题全部集中在"客户端工程"这一层**：一只 debug 签名的包、一条零校验的安装链、一个对所有页面开放的 JS 桥、一套只为鼠标写的交互，外加上线前那 45–300 秒的启动门。

按投入产出排序：**先花约 40 行代码斩断三条 P0 攻击链（1 天），再花 1 小时把启动门从"等语音引擎"改成"先进片库"（用户感知最大的一改），然后做上传与弹窗的两个功能缺口（1 天），最后才是触屏可用性（2–3 天）。** 做完这四步，它就从"能用的网页"变成"能放心装在家人手机上的客户端"。

## 3. 四个「必须马上处理」的问题（且都很便宜）

### ① 你的运行时是「无密码 + 全局明文 + 免鉴权分发」三件套

- **实测**：`%APPDATA%\CinemaVault\runtime\config.json` 里 `auth.enabled=false`、`password=""` → `server.js:48` 直接放行，整个 `/api/*`（含 `POST /api/config`、`/api/scanner`）在同网段内裸奔；`server.js:45` 又把 `/app` 放进 `PUBLIC_API_PREFIXES`，所以**即使你开了密码，`/api/app/*` 依然免鉴权**——任何能连上 3517 的设备都能下载 APK，版本接口还是完美的「这台机器在跑 CinemaVault」指纹探针。
- **为什么现在危险**：局域网内"能连上"的设备不只有你的手机（访客 Wi-Fi、智能电视、被入侵的 IoT）。你还在用 Cloudflare 穿透做外网访问——一旦穿透域名被扫到，这就是一个无口令的私人媒体库 + 一个免鉴权下载点。
- **修法（XS，1 小时）**：① 给 `/api` 加一条启动告警日志（`auth.enabled=false` 时打印"局域网内任何设备都可无凭据访问"）；② 把 `/app` 从白名单里拆出来，改为「短时效签名 URL」（`?exp=&sig=`，服务端 HMAC）或要求会话；③ 若外网穿透在用，强制开启密码。
- **已核验"没问题"的**：`GET /api/config` 的脱敏是对的（`routes/config.js:71` 删 `tmdbApiKey`、`:73-77` 只回 `enabled/hasPassword`）；静态目录不会泄露 `config.json`/`cache.db`/`.git`（全 404）；反代 SSRF 有 `hostInSite` 主机白名单兜底。

### ② 安装链的「信任根」现在是空的

- **四个环节全开**：`MainActivity.java:272-275` 导航不设防（`return false`）→ 任意站点留在同一 WebView、桥继续暴露；`:265` 的 `@JavascriptInterface` 是 per-WebView 而非 per-origin → 任意 frame 都能调 `:144-147 triggerUpdate`；更隐蔽的是 `:302-305` 把**当前页面 origin** 当更新源，任何页面返回 `{"versionCode":99,"apkUrl":"http://evil/x.apk"}` 就能弹原生安装框；`:734-757` 下完直接装，无 sha256、不比对签名证书；`routes/app-update.js:63-98` 也不下发 hash。
- **叠加一条**：分发件是 `CN=Android Debug` 签名（三包同证 `eb5a7571…`，与 `app-debug.apk` 的 SHA-256 完全相同 `e885d528…`）+ `debuggable=true`。debug key 口令是公开的 `android`，**任何人都能签一个同包名的包覆盖安装你的 App**，并继承你的 WebView 私有数据。
- **修法（M，1.5 天）**：导航白名单（外部域名甩 `ACTION_VIEW`）+ 删掉 `onCreate`/`onNewIntent` 里 `else { loadServerUrl(uriStr); }` 的任意 URL 分支 + 更新源改读 `SharedPreferences` 而非当前页面 + 服务端下发 `sha256`/`signerSha256` 并在客户端 `MessageDigest` 校验、与自身证书比对 + 建自己的 keystore（自签即可，不需要任何机构）。
- **注意**：`android/` 整个模块**没进 git**（`git ls-files android/` = 0，仓库却跟踪了 16357 个文件）。上面所有修复都会没有历史、无法回滚、无法评审——**这是"先做"而不是"顺带做"的事**。

### ③ 两个"每天都在踩"的功能缺口，用户以为是自己操作错了

- **`<input type="file">` 全部失效**（4 处：`library.html:677` 上传封面、`app.js:7610/7622/7651` 壁纸/横幅/动效）：`onShowFileChooser` 未实现（`MainActivity.java:330-356` 只覆写了 `onShowCustomView`），点开无反应、无报错。
- **`window.open` 全部静默丢弃**（17 处：`app.js:4246/4304/4913/5272/5501/5573/5594/6187/6222/7441/16821`、`features.js:1580/1638/1781/1958`、`home.js:481`、`media-source.js:229`，含**云盘 OAuth 下载**与"外部浏览器打开"）：`onCreateWindow` 未实现。修法不是真开新窗口，而是用 `Transport` 拿回 URL → 外部域名交给 `Intent.ACTION_VIEW`，内部 URL 当前 WebView 加载（S，半天，顺带解决"站点被 UA/X-Frame 拦"）。

### ④ 启动门在等语音引擎，而不是在等片库（体验第一杀手，修起来 1 小时）

这是本轮最"值钱"的发现，因为它隐藏在"慢"的印象背后，实际是**设计决策问题**：

- `app.js:16243-16296`：`initBootGate()` 铺一张全屏遮罩，轮询 `/api/tts/status` 等语音引擎（IndexTTS/Breeze/VITS/GPT-SoVITS）ready 才揭开；`skip` 按钮 45 秒后才 `visibility:visible`（`library.html:1077`、`app.js:16292`），硬上限是 `if (el >= 300) return finish();`——**最长 5 分钟**（`app.js:16293`）。顺带一处文档 bug：函数头注释 `app.js:16242` 写的是"120s 强制放行"，与代码的 300s 不符。
- **它不是随手写的**：注释 `app.js:16238-16242` 说明了动机——"EXE 启动 15s 后自动预热 TTS，模型加载 1-2 分钟内整机满载；旧版用户此刻已进主页 → 点朗读无声、界面卡顿、体验割裂"，所以拿全屏门挡住。这个判断在**桌面**上成立，但搬到手机上代价翻倍：主网格 0.8 秒就绪，**它明明已经能用，却因为"TTS 没预热完"不让用户看见**；Wi-Fi 慢或引擎冷启动慢时，用户面对的是"不可操作的黑屏 45 秒起、最长 5 分钟"，而且没有重试入口。
- **修法（S，约 1 小时，不是简单删掉这段）**：把"挡住整个应用"降级为**只挡语音相关入口**——
  1. 启动门只等「片库接口 + 首批海报」，3 秒内进主页；
  2. TTS 预热改后台进行，顶栏给一个"语音加载中"角标，朗读按钮在未就绪时显示进度而不是报错；
  3. 手机端（`UA 含 CinemaVault-Android` 或 `window.AndroidBridge` 存在）**默认不自动预热**，改为首次点朗读时才拉起引擎。
- 顺带值得追问的根因：引擎冷启动 1–3 分钟本身才是病根。如果它只用于听书，可考虑"按需启动 + 首次朗读时一次性提示"，或在服务端为常用书预生成音频缓存（Legado 的段级缓存思路，见 04 报告）。**这一个改动对"这个 App 用起来顺不顺"的影响，超过其他所有性能优化之和。**

### 主题 C · 「网页套壳」到「客户端」的能力缺口（来自 04 调研）

按用户价值排序，缺的都不是小功能，是**让"私人媒体库"这个叙事成立的关键一环**：

1. **听书没有后台播放**（`MediaSessionService` + `mediaPlayback` 前台服务 + `POST_NOTIFICATIONS`）——切 App 就断，TTS 这个卖点被"锁屏即停"抵消。**P0，M**
2. **局域网自动发现 + 扫码配对**（`NsdManager` + `MulticastLock` / 一次性 token 二维码）——消灭"手输 IP"这个唯一入口的流失点；顺带修掉 `MainActivity.java:183` 默认 `10.0.2.2:3517`（模拟器专用地址，真机首次必连不上）。**P0，S–M**
3. **原生播放器 MVP**（Media3 ExoPlayer + 内置字幕 + 系统 PiP + 手势层）——WebView `<video>` 无后台音频、字幕弱、PiP 不稳、耗电高。**P0，M–L**
4. 离线下载（`DownloadManager`/自研断点 + WorkManager，不能挂 `dataSync` 前台服务硬扛——Android 15 有 6h/24h 上限）、投屏 DLNA、通知渠道化、分享接收（`ACTION_SEND video/*`）、应用锁、浏览器壳兜底……
5. **明确不建议**：上架 Play、TWA（国内无 Chrome）、Compose 重写 UI、Kodi 式插件体系、为保活做 FGS 长连接。

### 主题 E · 性能与体积（02-h5 详述）

网页层是「桌面优先 + 移动补丁」的典型形态：**`public/js/app.js` 单文件 873KB 未压缩**、60+ 个 JS / 40+ 个 CSS 靠 `?v=N` 手写版本号、首屏同步脚本链过长。这一层不需要重写，但需要"拆包 + 懒加载 + 移动端样式降级开关"。

02 报告把这一层量到了字节级，结论比"有点大"严重得多：

| 问题 | 实测证据 | 成本 |
|---|---|---|
| **启动门（bootGate）在等语音引擎，不是在等片库**：全屏遮罩轮询 `/api/tts/status`，引擎 ready 才揭开；45 秒后才显示「跳过」，硬上限 `300` 秒 | `app.js:16243-16296`（注释写"120s 强制放行"，代码是 `if (el >= 300) return finish();` —— 注释已过期） | S |

| **404 KB 的 `hls.min.js` 在首屏同步 `<script>` 加载**，但只有点「播放」才用到 | `library.html:1012` | S |

### 主题 F · 平台合规与未来（04 详述）

- **targetSdk 36 已是 Play 门槛（2026-08-31 生效）**，你停在 34。侧载不受约束，且**暂时白拿了旧行为兼容**（edge-to-edge 强制只对 ≥35 生效、predictive back 默认化只对 ≥36 生效）。
- 但**升 35 的唯一阻断项是"零 insets 处理"**（`MainActivity.java:165-168/827-842` 用已废弃 `setSystemUiVisibility`），要一起做：`setDecorFitsSystemWindows(false)` + `WindowInsetsListener` + `WindowInsetsControllerCompat` + H5 侧 `env(safe-area-inset-*)`（注意 Android WebView 里 `safe-area-inset-top` 恒为 0，见 05-07）。预估 1–2 人日 + 一次全页面回归。
- 16 KB page size **当前 N/A**（APK 内 0 个 `.so`），但一旦引入 Media3 + FFmpeg/libass，就是准入清单上的一条硬约束。
- 侧载真正的痛点是 **Play Protect 对 debug/未知来源的拦截**（"unsafe app blocked"），以及每个来源要单独授权"安装未知应用"——换成 release 签名能显著减少这类摩擦。
