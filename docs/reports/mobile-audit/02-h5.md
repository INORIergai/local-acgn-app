# 02 · H5 / WebView 移动端前端审计

> 范围：`public/library.html`（主界面）、`public/js/app.js`（852.9 KB 单体）、`public/css/*`（56 个）、移动层 `mobile.css` / `mobile-gestures.js` / `mobile-nav.js` / `mobile-updater.js`、三维阅读器 `comic-reader.html` / `novel-reader.html` / `cloud-reader.html`，以及它们共同依赖的原生桥 `AndroidBridge` 与 `SwipeRefreshLayout`。
> 方法：只读静态审计 + 字节级量化。正则抽取 `library.html` 的全部 CSS/JS 引用后去重、`fs.statSync` 累加真实字节；`zlib` level9 抽样实测 gzip 比；正则统计 CSS 规则块 / `!important` / `backdrop-filter` / `@keyframes` / `infinite`；`Select-String` 定位调用点。**未启动服务器、未跑 Playwright、未连接真机**，网络耗时结论按 4G（下行 9 Mbps / RTT 170 ms）模型推算并已标注。与 [03-backend.md](03-backend.md) 的分工：03 管接口/缓存/数据，本篇管浏览器侧执行成本、手势与桥契约。
> 阅读约定：每条按「现象 → 影响 → 改法 → 工作量」四段，工作量用〔S/M/L〕标在改法行末。

**一句话结论**：这不是"某个页面慢"，而是**一台中端机每次启动被要求吞下 2.58 MB / 86 个请求，然后先看 45~300 秒的全屏遮罩**。性能问题里约 70% 靠删资源（hls、52 个 CSS、AI 模块）就能解决；但 `bootGate`、常驻 1.5 秒轮询、无离线兜底这三条不修，加多少带宽都压不住体感。

## 1. 首屏与加载预算

### 1.1 实测网络预算

```text
public/library.html          1,109 行 / 73,207 B
<link rel=stylesheet>        52 个（行 8-138）      合计 679,852 B = 663.9 KB
<script src>                 33 个（行 1012-1055）  合计 1,950,298 B = 1904.6 KB
                             ──────────────────────────────────────────────
                             86 个请求 / 2,640.0 KB；gzip 比 ≈26% → 约 686 KB
```

单文件最大的几块（原始字节 / gzip 实测）：

| 资源 | 原始 | gzip | 首屏必需 |
|---|---|---|---|
| `js/app.js` | 874,744 B (852.9 KB) | 223,679 B (26%) | 是（其中只有 ~15% 是首屏） |
| `lib/hls.min.js` | 413,952 B (404.2 KB) | 124,697 B (30%) | **否**，点播放才需要 |
| `js/features.js` | 124,589 B | 35,618 B (29%) | 否 |
| `js/av-board.js` | 75.3 KB | — | 否 |
| `css/style.css` | 76,227 B | 14,507 B (19%) | 是 |
| `css/polish.css` | 71,311 B | 17,776 B (25%) | 大部分否 |
| `css/round-motion-extras.css` | 63,288 B | 13,785 B (22%) | 否（纯动效） |

**现象**：`library.html:1018` 是同步 `<script src="js/app.js?v=139"></script>`，前面 1012 行还压着 `hls.min.js`；52 个 `<link rel=stylesheet>`（8-138）全部阻塞渲染。
**影响**：4G 下 86 个请求光 RTT 就 ≈2.5 s，加 1904 KB JS 传输 ≈1.7 s、解析执行 app.js 17,465 行 ≈0.8~1.5 s（中端机），**DOMContentLoaded → 首帧实际落在 4~6 s**，`bootGate` 还会再往后推（见 1.2）。LCP 预算现状超标 2 倍以上。
**改法**：① `server.js:116` 加 `compression()`，2.58 MB → ~686 KB；② `library.html:1012` 的 hls 改由 `showVideoPlayer()`（`app.js:14222`）首次调用时动态注入，首屏 −404 KB / −1 请求；③ `library.html:1018` 的 app.js 加 `defer`（33 个脚本里目前只有 1052-1055 这 4 个有）；④ 预算写进检查清单：**Fast 4G LCP ≤ 2.5 s、TTI ≤ 3.5 s、首屏 gzip JS ≤ 250 KB、请求 ≤ 30**，现状差距 7.6× / 2.9×。〔M〕

### 1.2 bootGate 是真正的 P0：不是加载慢，是"故意不给你看"

```js
// public/library.html:1062,1073
#bootGate { position: fixed; inset: 0; z-index: 4000; ... background: rgba(10,10,16,0.96) }
#bootGateSkip { visibility: hidden; }
// public/js/app.js:16292-16293
if (el >= 45 && skipBtn) skipBtn.style.visibility = 'visible';
if (el >= 300) return finish();
```

**现象**：`init()`（`app.js:16304`）第一行就调 `initBootGate()`，先铺 96% 不透明全屏遮罩，再 `fetch('/api/tts/config')`（16259）并**每秒**轮询 `/api/tts/status?all=1`（16270）；跳过按钮 45 秒后才可见（16292），自动放行上限 300 秒（16293）。
**影响**：① LCP 被遮罩彻底顶掉——网格 0.8 s 就绪也看不见，体感从"慢"变"像卡死"；② 弱网/PC 睡眠/TTS 服务不响应时，用户面对 45 秒不可操作黑屏且**无跳过无重试**，这是 P0 级可用性缺陷；③ 这段窗口额外打出 45~300 个轮询请求。
**改法**：① 16292 的 45 → **1.5 秒**，16293 的 300 → **8 秒**；② 遮罩改 `background: rgba(...,0.55)` 并只覆盖网格区，让骨架屏先可见；③ TTS 不应阻塞首屏，把 `initBootGate()` 从 `init()` 第一行挪到 `switchView('home')`（16337）之后；④ 轮询 1000 ms → 3000 ms，`visibilityState==='hidden'` 时暂停。〔S〕

### 1.3 52 个 CSS、6 轮 round 覆盖

量化（`public/css` 56 文件 / 746.1 KB）：规则块 **4350**、`!important` **1222**、`backdrop-filter` **138**、`filter:` **207**（含 `blur(` **139**）、`box-shadow` **374**、`transform:` **551**、`@keyframes` **127**、`animation:` **172**（`infinite` **37**）、`will-change` **21**、`@media` **126**、`content-visibility`/`contain` 仅 **5**。
毒瘤单文件：`round-motion-extras.css`（`library.html:52` 加载）402 规则 / **469 `!important`** / 38 `backdrop-filter` / 52 `blur()` / 48 `animation` / 36 `@keyframes`；另有 `style.v2-backup.css`（73.9 KB）**未被任何页面引用**却留在仓库。

**现象**：52 个样式表串行解析，同一批卡片/弹层被 `round13 / round34 / round42 / round113 / round113-motion / round-motion-extras / polish` 反复覆盖，只能靠 `!important` 打赢。
**影响**：① 阻塞渲染 664 KB；② 样式重算成本高，滚动更易掉帧；③ 改一个卡片阴影要试 6 个文件，`round-motion-extras.css` 469 个 `!important` 意味着后续任何人只能继续加 `!important`。
**改法**：① 零风险起步：删 `style.v2-backup.css`，把 469 个 `!important` 中的颜色/字重类批量降级；② 6 个 round 动效文件物理合并为 `css/motion-pack.css`（保序拼接），请求 52 → ~20；③ 动效用 `<link media="print" onload="this.media='all'">` 异步加载；④ 首屏关键 CSS（grid/tabbar/文字，约 12 KB）内联进 `<head>`。〔L〕

### 1.4 `?v=N` 实际收益为 0

```js
// server.js:110-116
app.use((req,res,next)=>{ if (req.path.endsWith('.html')) res.set('Cache-Control','no-cache'); next(); });
app.use(express.static(path.join(__dirname, 'public')));   // ← 无 maxAge、无 compression
```

**现象**：HTML 里有 82 处 `?v=N`，但 `express.static` 默认 `max-age=0` + ETag，每个资源每次启动仍要发条件请求。
**影响**：`?v=N` 只保证"能更新"，没换来"不下载"——85 个 304 往返 ≈1.4 s RTT 白花，服务重启/换 IP 时更明显。
**改法**：`server.js:116` 改 `express.static(..., { maxAge: '30d', immutable: true })`（失效交给 `?v=`），HTML 保持 `no-cache`；二次启动请求数 85 → 1。〔S〕

### 1.5 骨架屏与渐进渲染

`polish.css:1508-1533` 有 `.nr-skeleton-*` + `nrShimmer 1.4s linear infinite`，但**只服务于小说阅读器**；主网格在数据回来前是空白，靠 bootGate 遮罩"掩盖"。
**现象/影响**：首屏唯一可见元素是遮罩；数据失败时空 grid 与"加载中"无法区分。
**改法**：`library.html` 的 grid 容器预置 12 个纯 CSS `.card-skeleton`（≤8 KB），`renderMoviesChunked`（`app.js:2571`）首批写入时自然替换，`appendChunk`（2590）无需改。〔S〕

### 1.6 字体与图标（健康，无需改）

`@font-face` **0 处**、`@import` **0 处**、无图标字体；用系统字体栈 + `icons.js`/`nav-icons.js` 内联 SVG → 无 FOIT/FOUT、无字体请求。

## 2. 滚动与渲染性能

### 2.1 分批渲染方向对，但每批全量重算氛围光

```js
// public/js/app.js:2571-2572,2606
function renderMoviesChunked(movies, title) { ... const CHUNK = 60; ...
    applyAmbientGlow(grid);        // 每追加 60 张就整体重算一次
```

**现象**：分批 60 + `IntersectionObserver`（`app.js:2614-2624`，`rootMargin:'600px'`）续批是对的，但 `applyAmbientGlow` 每批对**整个 grid**（含已渲染卡）重算。
**影响**：第 2/3 批时 grid 已有 120/180 卡，重算线性增长，滚到第 3 批附近可感卡顿。
**改法**：只处理本批新增节点（`appendChunk` 已持有 `newCards`，`app.js:2590-2609`），或只对首屏可视 12 张生效。〔S〕

### 2.2 滚动监听与 layout thrash

| 位置 | 代码 | 问题 |
|---|---|---|
| `app.js:1176-1186` | `strip.addEventListener('scroll', () => { ... getBoundingClientRect() ... doWavePhysics() })` | 每次 scroll 同步读布局再写样式，读写交替 |
| `app.js:13887-13890` | `listEl.addEventListener('scroll', ...)` 隐藏悬浮预览 | 无节流 |
| `round113-header.js:62-63` | `document.addEventListener('scroll', kick, true)` + `window.addEventListener('scroll', kick)` | 同一逻辑捕获+冒泡双跑 |
| `features.js:700-705` | `window.addEventListener('scroll')` + 250 ms 节流 | **全库唯一一处节流** |
| `av-board.js:1061` | slider `scroll` | 无节流 |

全库**无 debounce/throttle 工具函数**（0 命中），`getBoundingClientRect` 共 25 处（app.js 13、round113-flip 7、motion-flip 5）。
**改法**：加一个 `rafThrottle(fn)`（10 行）包住上表 5 处；`app.js:1176` 的 `doWavePhysics` 拆成"读阶段/写阶段"两段。〔S〕

### 2.3 合成层与滤镜滥用（移动 GPU 压力最大的一块）

`backdrop-filter` **138** 处、`blur()` **139** 处、`infinite` 动画 **37** 处、`will-change` 21 处、`box-shadow` 374 处；最集中在 `round-motion-extras.css`（bf 38 / blur 52 / anim 48）与 `polish.css`（bf 13 / blur 14 / anim 28）。
**现象/影响**：卡片、弹层、标题普遍毛玻璃 + 常驻动画；`backdrop-filter` 是移动 GPU 最贵的合成操作之一，滚动时逐帧重算模糊；37 处 `infinite` 让 GPU 无法降频，**发热掉电**，这也是 2.2 掉帧的主因（不止 JS）。
**改法**：① 移动端 MQ（`max-width: 860px`）统一 `backdrop-filter: none` + 实色半透明底；② `infinite` 动画默认在移动端关闭，只在 hover/可见时跑，并复用已有 39 处 `prefers-reduced-motion` 写法；③ `will-change` 只留 3~5 个真正需要的。〔L〕

### 2.4 图片尺寸与 lazy loading

好的方面：`loading="lazy" decoding="async"` 覆盖 36 处（app.js 26、home.js 4、features.js 3、av-board.js 3）。缺的方面：**没有一张图带 `width`/`height`**，且服务端给原图（见 2.5）。
**现象/影响**：卡片高度在解码前为 0，滚动中列表不断"长高"，内容跳动（CLS）；`rootMargin: 600px` 在这种抖动下会误判/反复触发。
**改法**：卡片模板统一 `width="180" height="270"` + CSS `aspect-ratio`。〔S〕

### 2.5 海报：首批 60 张 = 8.6 MB

```js
// routes/movie.js:2065-2079
router.get('/poster/:hash', (req, res) => {
    const file = path.join(POSTER_DIR, req.params.hash);
    res.sendFile(file);          // 无 resize、无 Cache-Control
});
```

实测 `cache/posters`：**11,982 张 / 平均 144.3 KB / 最大 0.99 MB / 合计 1688.6 MB**；`CHUNK=60` → **≈8.6 MB/首批**。
**现象/影响**：网格一次拉 8.6 MB 原图（多为 1000px+），4G 下铺满需 6~10 s，且解码 60 张大图吃内存；弱网时就是"永远转圈"。与 [03-backend.md](03-backend.md) 的"无缩略图"同根因。
**改法**：① `routes/movie.js:2065` 支持 `?w=360`，生成并落盘 `cache/posters/w360/<hash>.jpg`；② 同时加 `Cache-Control: public, max-age=2592000, immutable`；③ 网格 `<img>` 改 `/poster/<hash>?w=360`，详情页用原图。〔M〕

### 2.6 漫画 / PDF 大图解码

```js
// public/comic-reader.html:1203-1214
const scale = (maxWidth || 1600) / baseViewport.width;
const viewport = basePage.getViewport({ scale: Math.min(scale, 3) });
canvas.width = viewport.width; canvas.height = viewport.height;
return canvas.toDataURL('image/jpeg', 0.9);
```

**现象**：PDF 页按 1600px 宽（`scale` 上限 3）全尺寸渲染到 canvas，再 `toDataURL('image/jpeg', 0.9)` 塞进 `<img>`；`1651` 另有一路 300px 缩略。
**影响**：A4 单页 1600×2263 ≈14.5 MB 位图，`toDataURL` 再产 base64（额外 ~1.5× 峰值内存）+ 同步主线程编码；翻几页后 WebView 纹理/堆压力陡增，低端机 renderer OOM 白屏，翻页瞬间卡顿。
**改法**：① 渲染宽度改 `window.innerWidth * devicePixelRatio`（手机约 1080 即可）；② `canvas.toBlob(cb,'image/jpeg',0.85)` + `URL.createObjectURL` 替代 `toDataURL`，翻页 `revokeObjectURL` 回收；③ 页缓存上限 3 页（保留 `1437-1444` 的 ±1/±2 预取但配合回收）。〔M〕

## 3. 手势与原生冲突

### 3.1 下拉刷新：`SwipeRefreshLayout` 与 H5 手势双轨

```java
// MainActivity.java:436 / 93-108 / 359-366
swipeRefresh.setOnRefreshListener(...);
public void setReaderMode(boolean inReader) { ... swipeRefresh.setEnabled(!inReader); ... }
webView.getViewTreeObserver().addOnScrollChangedListener(v -> {
    String url = webView.getUrl();
    boolean isReader = url != null && (url.contains("reader.html") || url.contains("comic") || url.contains("novel"));
    swipeRefresh.setEnabled(!isReader); ... });
```

**现象**：原生侧有**两套**判定：`onPageFinished`（289）判一次、每个滚动帧（359-367）再判一次；H5 侧 5 处又主动调 `setReaderMode`（`app.js:14202/14237/14357/14376/14409`）。
**影响**：① 阅读器是**以 iframe 打开**的（`library.html:965` readerView / `974` readerFrame，`app.js:14408` 只改 `iframe.src`），主框架 URL 恒为 `library.html`，原生 `url.contains(...)` **永不命中**——能正常工作完全依赖 H5 调 `setReaderMode` 成功；② 任一路径漏调/抛错（H5 侧 11 处桥调用全无 try/catch），阅读器里就会冒出下拉刷新 + 悬浮齿轮 + 状态栏，下拉还可能同时"刷新整页"与"下拉关闭弹窗"；③ `contains("comic"/"novel")` 是子串匹配，将来任何含这两词的 URL 都误判；④ 每帧 `getUrl()` + 三次 `contains` 是纯浪费。
**改法**：① 原生删 359-367 的每帧判定，`setReaderMode` 为唯一事实来源；② 保留 284-306 时改用 pathname 精确匹配 `/comic-reader.html`、`/novel-reader.html`、`/cloud-reader.html`；③ H5 11 处调用包 try/catch 并上报；④ 若坚持双轨，加 `isInReader()` 接口让原生 1 s 查一次而非每帧。〔M〕

### 3.2 阅读器翻页 vs Android 手势返回

```js
// public/comic-reader.html:1813-1822（novel-reader.html:1743-1762 同构）
area.addEventListener('touchend', (e) => {
    const dx = e.changedTouches[0].clientX - touchStartX;
    if (Math.abs(dx) > 45 && dt < 650) {
        if (dx < -45) { if (rtlMode) prevPage(); else nextPage(); }
        else if (dx > 45) { if (rtlMode) nextPage(); else prevPage(); }
    }
}, { passive: true });
```

**现象**：整个阅读区域都监听水平滑动，阈值 45 px（小说 40 px），三个监听全 `passive: true`、**从不 `preventDefault()`**。
**影响**：① Android 手势导航的边缘内滑（系统返回）在 WebView 里先被系统消费，**边缘起手的翻页变成"退出阅读器"**，表现为"翻页时好时坏"；② 因 `passive:true` 且不阻止默认，双指阶梯缩放（`1787-1811`）与 viewport 的 `maximum-scale=3.0` **同时生效**，缩放跳 1.3×/0.7× 台阶而非跟手；③ 纵向滚动容器与横向翻页没有 `touch-action` 隔离。
**改法**：① 翻页热区改"中间 70%"，左右各留 15% 给系统（或 `setReaderMode(true)` 时由原生 `setSystemGestureExclusionRects` 排除边缘）；② `comic-reader.html` 去掉 `maximum-scale=3.0`，缩放统一走 JS；③ 已在横滑态的 `touchmove` 用 `{passive:false}` + `preventDefault()` 换取跟手感；④ 容器加 `touch-action: pan-y`（已有 `magic-likes.css:63` 先例）。〔M〕

### 3.3 抽屉右滑与边缘竞争

```js

if (dx > 60) openDrawer(); else if (dx < -50) closeDrawer();
```

**改法**：抽屉改为"菜单按钮 + 内容区任意位置右滑（不限边缘）"，边缘让给系统；或原生排除左 24 px。〔S〕

### 3.4 safe-area 覆盖

全站 `env(safe-area-inset-*)` 仅 **13 处**：`mobile.css` 11（27-32 tabbar、84/439 底部留白、97-98 导航顶部）、`round20.css` 2、`comic-reader.html` 2（615/654）、`novel-reader.html` 6（334/338/346/363）、**`cloud-reader.html` 0**。

### 3.5 软键盘与 `visualViewport`

事实：`AndroidManifest.xml:32` 为 `adjustResize`；H5 侧 `visualViewport` **0 处**；`mobile.css:80` 用 `input,select,textarea{font-size:16px!important}` 防缩放（好习惯）。

## 4. 与 AndroidBridge 的契约

### 4.1 调用点：有存在性判断，无 try/catch

```js
// public/js/app.js:14357-14358
if (window.AndroidBridge && typeof window.AndroidBridge.setReaderMode === 'function') {
    window.AndroidBridge.setReaderMode(true);
}
```

分布：`app.js` 14202/14237/14357/14376/14409（true/false 成对）、`comic-reader.html` 1059/1832/1853、`novel-reader.html` 880/1769/1789；全库 `AndroidBridge` 出现 15 次。
**现象/影响**：存在性判断到位（普通浏览器不报错），但**无一处 try/catch**。桥对象在页面重载中/被回收后调用会抛 `Error: Java object is gone`，异常中断同函数后续逻辑——例如 `openComicReader` 的 iframe 赋值不再执行，表现为"点了漫画没反应"。
**改法**：加 `safeBridge(name, ...args)` 包装（10 行，try/catch + 静默 + `console.warn` 一次），替换 11 处。〔S〕

### 4.2 无版本协商；`setReaderMode` 与 URL 判定重复

`mobile-updater.js:11` 用 `navigator.userAgent.indexOf('CinemaVault-Android') !== -1 || !!window.AndroidBridge` 判"是否在 APK 里"，但**没有任何"桥支持哪些方法"的协商**。
**现象/影响**：APK 与 H5 独立升级（H5 随服务端、APK 要用户手动装）；H5 用了新桥方法而 APK 旧时，`typeof` 能兜住"方法不存在"，但**兜住后没有任何降级提示**，功能静默失效。叠加 3.1 的双轨判定，"是否阅读器"这一条事实有两个来源且原生那条永远猜错。
**改法**：① 加能力探测表 `const caps = { readerMode: typeof window.AndroidBridge?.setReaderMode === 'function', update: ... }`，初始化打 `console.info` 并暴露 `window.__bridgeCaps`，新功能按 `caps` 分支，缺能力时 toast 一次；② 原生删两处 URL 判定，见 3.1。〔S〕

### 4.3 `mobile-updater.js` 的版本比较与失败态

```js
// public/js/mobile-updater.js:18-32,121,130-132
if (ua.includes('4.5.4')) return 1; if (ua.includes('4.5.5')) return 2;
if (ua.includes('4.5.6')) return 3;  return 1;     // ← 兜底恒为 1
if (data.versionCode > currentCode) { ... }
catch (e) { if (!silent) alert('检测更新失败，请检查网络连接'); }
```

**现象**：版本号靠 UA 子串硬编码映射、兜底恒 1；`fetch('/api/app/android-version')`（107）**无超时**；失败用阻塞式 `alert`；`DOMContentLoaded` 后 `setTimeout(...,2500)`（143）弹窗，正好落在 bootGate 45 秒遮罩期内。
**影响**：① 每发一版 APK 都要改 H5 映射表，漏改就"永远提示"或"永远不提示"；② 弱网 fetch 挂起时弹窗永不出现；③ `alert` 在 WebView 里模态阻塞，可能被遮罩盖住且关不掉；④ 2.5 s 弹窗 + bootGate = 两个全屏层抢焦点。
**改法**：① 直接用 `AndroidBridge.getVersionCode()`（`MainActivity.java:125-132` 已有），取不到才退回映射并 `console.warn`；② 复用 `fetchJsonTimeout`（`app.js:10624`）设 8 s 超时；③ `alert` 改 toast/页内条幅；④ 弹窗时机改到 bootGate `finish()` 之后或 `requestIdleCallback`。〔S〕

### 4.4 桥不可用时的网页兜底

- `showUpdatePrompt`（`mobile-updater.js:95-100`）：有桥走 `triggerUpdate`，否则 `window.location.href = fullUrl` 下 APK —— 合理。
- 11 处 `setReaderMode`：`typeof` 后静默跳过，普通浏览器里阅读器 UI 不调整但功能可用（iframe 仍打开）—— 可接受。
- 缺口：`vibrate`/`toast` 无 `navigator.vibrate` / 页内实现兜底；`getVersionCode` 缺失时退化到 4.3 的硬编码表。

**改法**：`vibrate` 包 `if (navigator.vibrate) navigator.vibrate(ms)`；`toast` 用页内实现。〔S〕

## 5. 断网 / 弱网 / 服务重启

### 5.1 超时能力存在，只覆盖 3 个请求

```js
// public/js/app.js:10623-10636
async function fetchJsonTimeout(url, ms = 15000) {
    const ac = new AbortController();
    const timer = setTimeout(() => ac.abort(), ms);
    try { const r = await fetch(url, { signal: ac.signal }); return await r.json(); }
    catch (e) { return { code: -1, msg: e.name === 'AbortError' ? `请求超时（...）` : (e.message || '请求失败') }; }
}
```

全库 `fetch(` **226** 处、`AbortController` **1** 处，`fetchJsonTimeout` 调用点 **3** 处（10799 海报搜索 20 s、10801 抽帧 30 s、10803 `/api/config` 8 s）。
**现象/影响**：工具写得很好（返回 `{code:-1}` 而非 throw），但**主列表、详情、播放地址、搜索、通知**全是裸 `fetch`（`api.getMovies` `app.js:218`、`searchMovies` 233、`getMovieDetail` 239）。PC/NAS 睡眠唤醒或服务重启时 TCP 层可能挂 60~120 s，期间网格空、转圈不停，**用户没有任何"失败/重试"出口**——这就是"服务重启后必须杀进程重开"的成因。
**改法**：把 `fetchJsonTimeout` 提到公共文件（或 `core.js`），给 4 个 api 封装统一 `ms=10000` 并加失败态（网格"重试"按钮），复用现有超时文案样式。〔M〕

### 5.2 零离线能力

`public/*.html` 内 `serviceWorker` / `manifest.json` / `rel="manifest"` / `workbox` **0 命中**。
**现象/影响**：断网时 WebView 直接显示 `net::ERR_INTERNET_DISCONNECTED` 原生错误页——在 APK 里是白板 + 一行英文，用户无从操作，只能退出重进；也没有"上次内容"可看。
**改法**：① 最小 SW：`/library.html` + 关键 CSS/JS cache-first（配合 1.4 的 `?v=`），`/api/*` network-only；② 导航失败返回项目内 `offline.html`（"连接不到电脑，请检查是否同一 Wi-Fi" + 重试 + 上次服务地址）；③ 加 `navigator.onLine` + `online/offline` 顶部提示条。〔L〕

### 5.3 图片 404 降级只做了一部分

有 `onerror` 的：`app.js:653`（`POSTER_PLACEHOLDER`）、`4775`/`4997`（`this.remove()`）、`6207`（`nrCoverFallback`）；**网格主模板等大量 `<img>` 没有**。
**现象/影响**：海报被清理/换盘后卡片破图 + alt 文字，`this.remove()` 还会让网格出现空洞。
**改法**：`renderMoviesChunked` 卡片模板统一 `onerror="this.onerror=null;this.src=POSTER_PLACEHOLDER"`（复用 653 写法与常量）。〔S〕

### 5.4 HLS 播放器无错误恢复

```js
// public/js/app.js:14227-14233
if (isHls && window.Hls && window.Hls.isSupported()) {
    hlsInstance = new window.Hls({ maxBufferLength: 30 });
    hlsInstance.loadSource(videoUrl); hlsInstance.attachMedia(video);
} else { video.src = videoUrl; }
```

**现象/影响**：只初始化，全文**无 `hlsInstance.on(Hls.Events.ERROR, ...)`**，无 `recoverMediaError()`/`startLoad()`。局域网转码流在切前后台、Wi-Fi 抖动时必现 `bufferStalledError`/`mediaError`，播放器停住转圈，**用户只能退出重进**。
**改法**：加错误监听——`data.fatal` 按 `data.type` 分支：`networkError` → `startLoad()`（最多 3 次，退避 1/2/4 s）；`mediaError` → `recoverMediaError()`；仍失败 `video.src = videoUrl` 回退并提示"网络不稳，点击重试"。〔S，约 20 行〕

### 5.5 换网段/换 IP（提醒，主体归 03）

`server.js:104-106` 的 `/` 直接 302 到 `/library.html`，前端 API 全是相对路径；PC 的局域网 IP 变了（DHCP 续租）后，书签里的旧 IP 什么都连不上，而离线兜底缺失。建议 `offline.html` 里提供"修改服务器地址"输入框（NAS 媒体库标配）。

### 6.3 小说阅读器：分页算法是性能雷

```js
// public/novel-reader.html:1277-1295
for (; i < chapterBlocks.length; i++) {
    probe.insertAdjacentHTML('beforeend', chapterBlocks[i]);   // 写 DOM
    if (probe.scrollHeight > H + 2) { ... break; }             // 立刻强制读布局
```

**现象/影响**：离屏 probe 贪心分页，**每插一块就同步读一次 `scrollHeight`**，即 O(块数) 次强制回流；`paginate()`（1301）在每次打开章节、每次改字号（`currentFontSize` 819）都会跑。300 段章节 = 300 次 reflow，中端机 200~500 ms 主线程阻塞，表现为"打开章节白一下/改字号卡一下"。

**改法**：① `visibilitychange` 隐藏时 `clearInterval` 全部、恢复时重启；② `checkScanStatus` 1.5 s → 5 s，且只在"扫描中"状态跑；③ 15 s 的通知 live 与 60 s 的通知轮询合并成一条通道。〔S〕

### 7.4 无 lint / 无构建 / 无测试

`package.json` 无 `scripts` 字段、无 eslint/prettier 配置、无 CI；唯一质量门是人工。风险面：`try{}` 255 处 / `catch(` 282 处（大量空 catch 吞异常）、`innerHTML` 254 处（刮削来的标题是外部数据，XSS 面）。
**改法**：加 eslint 只开 `no-undef` / `no-unused-vars` / `no-empty` + prettier，CI 里只报告不阻断；新增 `innerHTML` 必须走 `esc()` 转义。〔S（报告级）/ M（修到零错误）〕
